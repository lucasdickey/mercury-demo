Closing the month from Claude Code

Steward is a month-end close agent for a founder whose company banks with Mercury. It reads the books, proposes the payments and transfers, and can't move a dollar on its own.

The job

I'm a technical founder, and every month-end I do the same dozen things in Mercury's dashboard: check where cash sits across accounts, see which bills are due this week and pay them, chase invoices that are late, and move idle cash out of checking into something that earns yield. None of it is hard. All of it is clicking.

I already work in Claude Code. I want to type “close the month” there, get back what needs doing with the payments ready to go, and have nothing move until I say so.

Why this shape

Why an agent in Claude Code. The brief asked for something headless on Mercury's API, aimed at its most ambitious API customers. They're technical founders and finance engineers who already work in a terminal with an agent beside them. An MCP server meets them there. Claude Code is also where approval works best today: it can show Approve / Decline inside the conversation. Claude.ai, ChatGPT, and Grok can't yet.

Why month-end close. It recurs, it's specific, and it touches every part of the API that matters for money: balances, transactions, recipients, invoices, payments, transfers, and approvals. If an agent can close the month, it can do most of what a founder wants from their bank.

The one rule: the agent can't move money. Steward only calls Mercury's request endpoints. There's no code path to a direct send, and it refuses production tokens outright. Every payment passes two gates:

Gate 1 · Claude Code

You approve the proposal

An Approve / Decline prompt inside the conversation.

Gate 2 · Mercury

A teammate approves the request

It waits in Mercury's own approval queue until someone approves it in the dashboard.

Then

Money moves

The transaction carries the request id back, so the trail is complete.

That's not caution for its own sake. It's the model Mercury already uses with Command and approval policies. Steward tests whether a third-party agent can use it too.

How we got here: brute force

We didn't start from a spec. We pointed the agent at Mercury's sandbox, let it walk into every wall, and logged each one. That's also the fairest test of an API meant for agents.

“Can a frontier model, given only your docs, make this work on the first try.”Jason Lemkin, SaaStr, on testing whether an API is agent-friendly

It didn't. In the order it happened:

  1. Getting a working token#39 · #44 · #70

    The propose-only token still required an IP allowlist, despite the docs. The first call failed anyway: the laptop connected over IPv6 and the allowlist was IPv4. Mercury's own CLI hits the same wall and has no way around it.

  2. Reading the books#46 · #47 · #49

    Reads worked, but could be quietly wrong. A misspelled filter returns all the data with a 200. start and end filter by creation date, not the posted date the dashboard shows. A third of transactions belong to a credit account that /accounts doesn't list.

  3. The first payment request#58

    400 invalidApproval: “Nobody else in this organization can approve this payment.” A one-person company can't use the approval queue at all, and the solo founder is exactly who wants this agent.

  4. Adding a second approver#62

    A second real user, a phone number, and mandatory two-factor, all for fake money. Then the request went through.

  5. Retrying#59 · #74

    Sending the same request again with the same idempotency key returned an error instead of the original request. An agent that times out can't tell “already done” from “failed.” Most write endpoints don't take a key at all.

  6. Finding the approval#63 · #64

    The API gives no link to it, and it isn't under Tasks. It's under Payments → Needs Approval, next to a second request the API couldn't see.

  7. Mercury's own tools#18 · #68 · #72

    The CLI gets a lot right: it won't run a money command without --yes and it catches mistyped flags. But payments transfer is a direct transfer sitting next to payments request; our agent ran it expecting an approval request, and only a missing scope stopped it. And an undocumented sandbox MCP host advertises transactions:request and transfers:request: the capability this project argues for looks like it's already being built.

Each wall is an entry in the friction log, with what to ship. Seventy-five in all, most of them small.

What it tells Mercury

Mercury's API is agent-readable but not agent-actionable. The right primitive exists: queue an action for a human to approve. Four things keep agents from using it:

  1. It isn't open to agents in production, and it's gated by an IP allowlist that hosted agents can't satisfy.

  2. A one-person company can't use it.

  3. Retries aren't safe.

  4. The API fails silently on the mistakes models make.

The sandbox MCP's scopes suggest Mercury is already on the first. The other three are smaller, and they're what separates a demo from something a founder would trust with real money.

On two-factor. Agent-readiness checklists count “requires a human with 2FA” against an API. Here it guards approving a money movement, not logging in, and that's the point.

Limits, stated plainly

  • Sandbox only. No production token, by design.
  • No receivables in the demo. The sandbox has no invoices, and creating them needs an allowlisted token. Invoice follow-ups are covered by tests.
  • Bills live outside Mercury. There's no Bill Pay API, so Steward reads bills from a file prepared before each demo.
  • Approval in chat is a developer-client feature today. Claude.ai and ChatGPT get an approve link instead, and hosting the app publicly brings back the allowlist problem.

What I'd do next

  • Move Steward onto the sandbox MCP's request scopes once they're documented, and retire its own write path.
  • Add a status tool, so “did it go through?” gets answered in Claude Code instead of the dashboard.
  • Package the close as a Claude Code skill a founder installs once and runs every month.
