What

What we decided to build

An MCP server plus a thin chat UI that runs month-end close for a small company on Mercury: cash position, overdue receivables, bills due, and the surplus that should be earning yield. Each finding becomes a typed proposal. Anything that moves money is queued for human approval inside Mercury — the agent has no path to move it on its own.

Section
Why

Why this is the spike

Mercury has already shipped the obvious things: Command (natural language inside the dashboard), an official CLI, a hosted MCP, and agent cards. Rebuilding any of those would be table stakes. What they have not shipped is an agent-safe write path outside the dashboard.

Their MCP is read-only because they don't trust the model to act. The answer to "we don't trust it" doesn't have to be "so it can't do anything." It can be "so it has to ask — twice."

The REST API already contains the pattern: request-send-money and request-transfer-money queue an action for a human to approve in the dashboard, and neither needs an IP allowlist because the approval is the control. Those endpoints are absent from the MCP, along with harmless writes like categorizing a transaction — which Mercury says is the #1 thing early users want.

So the spike is a working demonstration of the tier we think Mercury's MCP should add next, built on their own API, with the API critique carried by the artifact rather than a slide.

How it maps to the brief

  • Business judgment. Month-end close is the workflow every founder actually runs, and the one Mercury says its CLI users reach for first: cash position, pay what's due, put the rest to work. The agent does the assembly; the human keeps the signature.
  • API / CLI / MCP understanding. We consume the official CLI's JSON, wrap the REST API, and ship a sibling MCP that exercises stateless elicitation (MCP 2026-07-28) and the approval endpoints — and we catalog every paper cut by layer as we go.
  • Trust and simplicity. One mental model — propose, approve — identical to Command's.
  • Regulatory and operational tradeoffs. IP allowlists, dual approval, 45-day token hygiene, PII kept out of the model's context, and careful "advice" language.

Found

What the API taught us

Serverless hosts have no fixed IP. Mercury's write tokens require one.

A Read and Write token must be bound to an IP allowlist. Vercel functions, Cloudflare Workers, Lambda, and most agent runtimes egress from rotating, shared address pools; a laptop's residential IP changes too. Mercury's docs are candid — "we do not offer a way to circumvent this security requirement" — and point at NAT gateways and static-IP add-ons.

The consequence is not a nuisance; it's architectural. From Vercel, the only Mercury write path that works at all is the approval-queue path (request-send-money, request-transfer-money), because those endpoints trade the allowlist for dashboard approval. Propose-only isn't just the safe design — it's the only design the platform allows where agents actually get deployed. Mercury's own hosted MCP is presumably running into the same wall, which may be part of why it's read-only.

Recommendation: make the approval-queue tier a first-class OAuth scope (propose:payments, propose:transfers, write:categories) for MCP and API tokens, no allowlist required, and say so on the token-creation modal.

Selected findings. The ranked summary with a BLUF is in findings.md; the full log — 60 entries so far, tagged by layer (API · MCP · CLI · docs · sandbox · ecosystem), each with a proposed fix — is in the friction log. It keeps growing through the build.

blocks
No single OpenAPI document.
Each reference page inlines its own fragment with the entire schema tree. listtransactions.md is 45 KB, mostly international-wire schemas irrelevant to a GET. Five pages ≈ 200 KB of duplicate JSON into an agent's context.
publish /openapi.json; prune per-page fragments to referenced schemas
blocks
Scope catalog is undocumented.
Custom tokens have per-endpoint scopes; some need an allowlist. The list exists only in the dashboard modal. The spec says bearerAuth for everything. An agent can't reason about what token it needs.
x-mercury-scope + x-requires-ip-allowlist on every operation
blocks
No error schema.
Every 4xx is a bare description — "400": "Invalid body". Agents self-correct from structured errors; here they get prose. Rate limits are unpublished.
RFC 9457 problem+json with code / field / hint; document limits and Retry-After
blocks
No recurring-stream or merchant-enrichment endpoints.
Transactions carry MCC, merchant id, and a 39-value category enum — the raw material — but nothing says "this is a subscription," and merchant.id has no lookup. Plaid ships both.
GET /recurring (cadence, avg, last seen) and GET /merchant/{id}, also as MCP tools
costs
Approval requests emit no events or webhooks.
An agent that proposed a payment has no way to learn it was approved or rejected except polling.
approvalRequest.updated event
costs
MCP has no aggregate tools.
"Spend by category, last 90 days" means paging 1,000 rows into context. Mercury already computes these for the dashboard.
spendSummary, recurringStreams, idleCash server-side
blocks
Consumer chat clients can't render an approval.
MCP elicitation works in Claude Code, Cursor, VS Code, and the Vercel AI SDK. Claude.ai has an open request since April and errors on the new-spec result; Grok's client is tools-only and times out; ChatGPT shows no support. "Approve in chat" is a developer-client story today.
Mercury: return a dashboardLink on approval requests so any client can finish the loop by URL
blocks
Creating an invoice needs a read-write token with an IP allowlist.
Invoices don't move money, but AR writes carry the same allowlist rule as direct sends — so a Vercel-hosted agent can read receivables and never create one. There is no request-style analog.
drop the allowlist for AR writes, or add them to the no-allowlist Custom scopes
costs
No Bill Pay API, no invoice-reminder API, no documented sandbox contents.
Payables exist in the product but not the API, so "bills due" has to live outside Mercury. Overdue-invoice reminders are dashboard-only. The sandbox guide doesn't say what's seeded or what's missing beyond webhooks.
GET /bills; POST /invoice/{id}/remind; a "what's in the sandbox" table
good
llms.txt and the .md suffix work — genuinely.
Every page opens by pointing agents at the index. The Send Money guide's Supported / Client-Side / Not Available tables are best-in-class. OAuth on the MCP uses dynamic client registration with PKCE and a reserved-name rule so third parties can't pose as Mercury.

Shape

Architecture

Environment and tokens

  • One sandbox org plays the company. Every read and every queued write hits api-sandbox.mercury.com, and the approval shows up in the same sandbox dashboard. No production token exists anywhere in the build.
  • Only the request-* endpoints are called. Direct sends and direct internal transfers are not wired, so even a bug can't move money past a human.
  • MCP endpoint protection — a long random path segment plus a server-side check. Right for a demo we tear down; the presentation describes the real answer (we become an OAuth authorization server, as Mercury does).

Next

What would change about the API

  1. A propose scope tier for MCP and tokens, backed by the existing request-* endpoints, with no IP allowlist.
  2. Non-financial writes in the MCP: note, category, recipient invite.
  3. Aggregate tools server-side: spend summary, recurring streams, idle cash.
  4. One OpenAPI document, a scope catalog, and a real error schema.
  5. Events for approval requests, so an agent learns the outcome of what it proposed.
  6. Agent cards via API — today isAgentCard is read-only — plus a guide on funding x402 / MPP / AP2 sessions from an agent card.
  7. A payables surface (GET /bills) and an invoice-reminder endpoint, so month-end close can be fully agent-assembled.
  8. CLI: a --sandbox flag and auto-detection of the mercury_sandbox_ token prefix; sandbox docs: say what's seeded and what's missing.

What we'd do next with the prototype: replace the shared secret with real OAuth, wire webhooks so the chat learns when a queued payment is approved (production only — the sandbox has none), and point the same tools at a personal account read-only as an epilogue.
