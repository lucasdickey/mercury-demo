What the Mercury sandbox actually contains and returns, probed read-only with a Custom token (the eleven non-asterisk reads + Send Money with Approval; see scope-catalog.md). Reproduce with node scripts/recon/sweep.mjs <out.json>. Sample values are from the seeded org "Not A Real Company Inc."; account and routing numbers redacted. Friction entries referenced as [#n].

Sweep to yield ⚠️ 0 treasury; 2 savings. request-transfer has no Custom scope [#41] 1 sweep of $1,443,600 → savings; cannot be queued with this token
Approval queue ⚠️ One-member org: POST request-send-money → 400 invalidApproval [#58]. After adding a second member → 200 pendingApproval; same idempotency key retried → 400, not a replay [#59]. Approved by the second member in Payments → Needs Approval → request approved, ACH outgoingPayment −$12.34 sent in 15 s with requestId back-link [#66] Gate 1 accepted in chat → raw 400 (one member)

Bottom line: reads work; the seed data can't exercise AR, AP, or treasury, payments queue only once the org has a second approver [#58], and transfers need a scope that doesn't exist [#41]. The demo needs seeding, and seeding recipients/customers/invoices needs asterisked (allowlisted) scopes this token deliberately doesn't have [#45].

Response headers [#54]

Present: x-mercury-request-id, traceparent, cache-control: private, no-store. Absent: any rate-limit header (RateLimit-*, X-RateLimit-*, Retry-After). Also present on every API response: git-commit, ecs-task-name, ecs-task-id, mercury-honeycomb-link, and four Set-Cookies (incl. _SESSION) on bearer-token calls.
